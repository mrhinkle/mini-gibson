# Mini Gibson observational dataset card

## Summary

The Mini Gibson observational datasets contain sanitized coding-agent run
records over synthetic software-engineering fixtures. They were collected to
study tool use, repair attempts, verification, and failure recovery—not to
represent the full distribution of production software work.

The versioned releases are publicly available in the
[Mini Gibson repository](https://github.com/mrhinkle/mini-gibson).

The original [`433-v1`](releases/433-v1/) bytes remain available at their
published hash for reproducibility, but they contain user-specific local home
path prefixes. The v1.1 release changes only those prefixes to `<HOST_HOME>` and
is the recommended public redistribution artifact.

The row format is defined by
[`schema.observational.v0.1.json`](schema.observational.v0.1.json). Task
The currently shipped reusable-fixture subset is indexed by
[`tasks.manifest.json`](tasks.manifest.json) (95 tasks). The two historical
releases contain 185 distinct task identifiers, so the manifest is not a
complete reconstruction index for every released row.

## Collection

The records were generated by a coding agent using NVIDIA Nemotron 3.5
Lightning through OpenRouter with the CoreWeave provider. Each task used a
controlled fixture and an independent verification command. The release
README files record exact runtime versions, collection windows, outcome counts,
tokens, cost, and file hashes.

The data contains both successful and failed attempts. A verified label means
the recorded task verifier passed; it does not mean that a patch is generally
correct, secure, minimal, or production-ready.

## Intended use

Appropriate uses include:

- studying coding-agent tool behavior and failure recovery;
- building parsers, filters, redaction checks, and trajectory-quality rules;
- development-only fine-tuning experiments with explicit split controls;
- reproducing the aggregate observations documented by Mini Gibson.

The `TEST_OBSERVATIONAL` rows in `433-v1.1-sanitized` are public evidence but remain
excluded from Mini Gibson training. Anyone running a new experiment should
create and document their own contamination and exclusion registry.

## Important limitations

- Tasks are synthetic fixtures, not a representative sample of real merge
  requests or production repositories.
- The original fixtures saturated at high verified rates, so they are weak as
  a discriminating final benchmark.
- Records reflect one model, provider path, runtime, prompt family, and
  collection period.
- Model-generated text may contain mistakes even when a verifier passes.
- The harder release is development-only and contains just 105 rows.
- Public data cannot serve as a secret holdout. Treat its test split as a
  documented exclusion, not as an undisclosed benchmark.

These limits are why Mini Gibson moved its main comparison to fresh,
repository-based tasks and kept the separate 35-task final evaluation
operationally sealed.

## Privacy and security

Release preparation normalized user-specific home-directory prefixes and
scanned for API keys, tokens, private-key material, and credential references.
Generic synthetic-fixture paths such as `/tmp/...` are retained as part of the
recorded task behavior. Email-like strings use fixture domains (`x.com`,
`y.com`, `example.com`, and `b.com`). Credentials, raw environment dumps,
private hostnames, and model weights are not intentionally included.
The current bytes of the recommended v1.1 sanitized release and the v2-hard
release were rescanned with Gitleaks 8.30.1 on October 18, 2026; both
directory-only scans reported zero leaks. The legacy v1 path disclosure is
documented above and is not a credential-scan finding.

No sanitization process is a guarantee. Before redistributing or combining the
records with other corpora, users should repeat secret and privacy scans and
review the source-provider terms that apply to their use.
